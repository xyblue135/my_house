# 版本更新教程：程序如何对接 GitHub 自动更新

本文说明「我的家」App 的**版本发布 → 检查更新 → 下载安装**全流程：开发者怎么发版，App 怎么知道有新版本，用户怎么升级。

---

## 一、整体机制（一张图看懂）

```text
开发者                          GitHub                        用户手机
────────                       ────────                      ────────
改代码 → 提交 → 打 tag ──────► Actions 自动构建 ──────► App 启动时静默检查
         （如 v2.1.1）          ↓                       GET api.github.com/…/releases/latest
                          上传正式签名 APK                 ↓ 对比版本号
                          并创建 Release ──────────► 发现新版本 → 提示 → 用户
                                                  打开下载链接安装 APK
```

三个角色：

| 角色 | 做什么 | 用什么 |
| --- | --- | --- |
| 开发者（你） | 改版本号、提交、打 `v*` 标签 | 本地 git |
| GitHub Actions | 自动测试 + 构建**正式签名** APK，创建 Release 并附上 APK | `.github/workflows/apk.yml` |
| 用户手机 App | 每天自动检查一次 Releases；设置页可手动检查、下载 | GitHub Releases API |

## 二、开发者：发布一个新版本（3 步）

### 第 1 步：升版本号（两个地方必须一起改）

1. `frontend/package.json` → `"version": "2.1.2"`（App 内「当前版本」显示的就是它，构建时由 Vite 注入）
2. `frontend/android/app/build.gradle` → `versionCode` 加 1（**必须递增**，否则系统不允许覆盖安装）、`versionName` 改成同样的 `2.1.2`

### 第 2 步：提交并推送

```powershell
git add -A
git commit -m "release: 2.1.2"
git push origin master
```

### 第 3 步：打标签触发发布

```powershell
git tag v2.1.2
git push origin v2.1.2
```

推送标签后，GitHub Actions 自动：运行测试 → 构建 Web → 同步 Capacitor → **用你的证书签名** → 创建 **Release** 并附上 `app-release.apk`。1~2 分钟后在仓库的 **Releases** 页面就能看到。

> 注意：标签必须推到 GitHub（`git push origin v2.1.2`）。只打在本地不会触发构建。

## 三、App 是怎么「对接」GitHub 的（原理）

App 里没有任何服务器。检查更新就是调 GitHub 的公开 API：

```text
GET https://api.github.com/repos/{所有者}/{仓库}/releases/latest
```

返回最新 Release 的 `tag_name`（版本号）、`body`（更新说明）、`assets`（附件列表）。App 做三件事：

1. **对比版本**：把 `tag_name`（如 `v2.1.1`）与 App 当前版本（构建时注入的 `package.json` 版本号）逐段比较
2. **提示**：比当前新 → 设置页显示「发现新版本 v2.1.1 + 下载 v2.1.1」按钮；顶栏「本机数据」弹层里也会出现提示
3. **下载**：点下载 → 打开 Release 里 APK 附件的 `browser_download_url` → 系统浏览器开始下载 → 下载完点开安装

代码位置：

| 文件 | 职责 |
| --- | --- |
| `frontend/src/composables/useAppUpdate.ts` | 检查逻辑（Releases API、版本比较、24 小时节流） |
| `frontend/vite.config.ts` | 构建时把 `package.json` 版本号注入为 `__APP_VERSION__` |
| `.github/workflows/apk.yml` | tag 触发的构建与 Release 发布 |

**为什么这样设计**：单机 App 没有自己的服务器，而 GitHub Releases 本身就是免费的版本托管 + 更新说明 + 下载加速（国内直连不稳定时可走代理或用 Gitee 镜像仓库，App 的「更新检查仓库地址」可以改）。

## 四、用户：怎么更新到新版本

1. **数据先行**：设置 → 云同步 → **推送到云端**（保证手机本地数据已备份到仓库）
2. 打开 App → 设置 → 检查更新 → 会显示「发现新版本 vX.Y.Z」→ 点 **下载 vX.Y.Z**
3. 浏览器下载完成后点开安装（与当前版本签名一致，**直接覆盖安装**，数据不受影响）
4. 装完打开就是新版本；也可以设置 → 云同步 → **从云端拉取**，把其它设备的新数据同步过来

> ⚠️ 唯一会丢数据的操作是**卸载**。遇到"签名不一致无法安装"时（例如从调试包装正式包），先推送到云端 → 卸载 → 装新包 → 初始化页「从云端导入」。

## 五、常见问题

| 问题 | 原因与处理 |
| --- | --- |
| 检查更新提示「该仓库还没有发布过版本」 | 代码仓库一个 Release 都没发过；先按第二节打 tag 发一版 |
| 检查更新一直失败 | 代码仓库是**私有**的（公开 API 读不到）或网络连不上 GitHub。把代码仓库设为公开，或给 App 的更新令牌开代理；数据仓库的私有性不受影响 |
| 安装提示"签名不一致" | 手机上装过别的签名的包（如旧的调试包）。先推送数据 → 卸载 → 装新包 → 从云端导入 |
| CI 里 Release 发布报 "Resource not accessible" | 工作流缺 `permissions: contents: write`（已配置）；检查是否改动了 workflow |
| 版本号没变导致不提示 | 发版时**两个版本号都要改**：`package.json` 的 version（App 内显示/比较用）和 `build.gradle` 的 versionName/versionCode（系统覆盖安装判断用） |
